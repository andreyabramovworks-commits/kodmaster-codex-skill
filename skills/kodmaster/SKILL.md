# KodMaster v4

KodMaster понимает намерение пользователя, выбирает минимально достаточный маршрут и загружает только нужные внутренние инструкции. Slash-команды необязательны: явная команда лишь снимает неоднозначность.

## 1. Сначала определить намерение

Явная команда имеет приоритет. Иначе сопоставить смысл запроса:

- план, оценка, «сначала разберись», «ничего не меняй» → `/kodplan`;
- аудит приложения, кода, архитектуры, ошибок, нерабочих сценариев → `/kodaudit` в режиме Discovery;
- проверить diff, результат Codex, готовность к merge/release → `/kodaudit` в режиме Acceptance;
- интерфейс, UX, внешний вид, responsive, accessibility → `/uiaudit`;
- исправить, реализовать, выполнить согласованный план → `/apply`;
- передать согласованный план Codex и провести полный lifecycle → `/kodsend`;
- грамматика, перевод, стиль или тексты → текстовый профиль из `references/writing-and-localization.md`;
- помощь → `/kodhelp`.

При смешанном запросе выбрать основной маршрут и добавить только релевантные профили. Подробная маршрутизация: `references/routing-and-depth.md`.

## 2. Режим глубины

- **Fast** — только указанный scope, прямые зависимости и дешёвые проверки. Не выдавать вывод о всём приложении.
- **Deep** — обязательная карта всего репозитория и полный проход по всем применимым трекам; ничего не пропускать молча.
- **Adaptive** — по умолчанию. Расширять scope по риску и доказательствам. Запрос «проверь всё приложение» трактовать как полный подробный аудит, близкий к Deep.

`/fast` и `/deep` являются модификаторами следующей или текущей задачи, а не отдельными целями.

## 3. Progressive disclosure

Всегда прочитать:

1. `references/routing-and-depth.md`;
2. файл выбранной команды из `commands/`;
3. только профили, выбранные матрицей ниже.

| Сигнал | Обязательный профиль |
| --- | --- |
| Любой технический аудит | `references/audit-engine.md`, `references/technical-audit.md` |
| Баг, падение, flaky, нерабочий сценарий | `references/debugging-and-tests.md` |
| PostgreSQL, SQL, Supabase, миграции | `references/database-audit.md` |
| React, Next.js, компоненты, frontend performance | `references/react-audit.md` |
| UI/UX/a11y | `references/ui-audit.md` |
| Тексты, перевод, грамматика, voice/tone | `references/writing-and-localization.md` |
| Заимствованные методики или лицензии | `references/methodology-sources.md` |

Не читать остальные профили «на всякий случай», кроме Deep-аудита: в Deep прочитать все применимые к реально найденному стеку профили.

## 4. Инварианты качества

- Сначала факты, воспроизведение и первопричина; затем исправление.
- Находка без проверяемого доказательства — гипотеза, а не баг.
- Для кода указывать `file:line`, путь выполнения или минимальное воспроизведение.
- Отделять `CONFIRMED`, `LIKELY`, `NEEDS_VERIFICATION` и `NOT_ASSESSED`.
- Не считать отсутствие совпадений поиска доказательством отсутствия проблемы.
- Не заявлять полное WCAG-соответствие по одному скриншоту или статическому анализу.
- Не выполнять активный pentest живого сервиса без явного разрешения и согласованного scope.
- Не публиковать секреты, персональные данные и exploit payloads в отчётах.
- Сохранять существующие соглашения проекта; KISS/YAGNI/SOLID — инструменты, не догма.
- Не трогать generated/vendor/lock/migrations без причины и не расширять рефакторинг за scope.
- При изменениях защищать грязный worktree и не уничтожать чужие правки.
- Проверки должны быть соразмерны риску, а финальный статус — правдивым.

## 5. `/kodaudit`: одна команда, два внутренних режима

**Discovery** — read-only аудит приложения. Результат: доказательные находки, первопричины, влияние, план исправления и вердикт `SHIP | FIX | BLOCK`.

**Acceptance** — проверка существующего diff/ветки/результата Codex. Результат: `GO | REWORK | BLOCKED | EVIDENCE_REQUIRED`. `GO` нельзя выдавать без проверки реального diff и достаточных тестов.

Если контекст неоднозначен, определить режим по наличию согласованной задачи и проверяемого diff. Если оба нужны — сначала Discovery, затем отдельная Acceptance после изменений. Старый `/audit` — совместимый алиас Discovery, но не показывается как основная команда.

## 6. Исправление багов

При просьбе «найди и почини»:

1. Выполнить Discovery.
2. Сформировать реестр кандидатов и дедуплицировать общую первопричину.
3. Для каждого исправляемого дефекта получить красное воспроизведение или явно объяснить, почему оно недоступно.
4. Внести минимальное исправление первопричины.
5. Добавить регрессионный тест на самом низком подходящем уровне.
6. Выполнить variant sweep по похожим путям.
7. Провести Acceptance по итоговому diff.

После трёх неудачных вариантов исправления остановиться и пересмотреть гипотезу/архитектуру, а не продолжать случайные патчи.

## 7. Планирование и автономность

`/kodplan` не меняет файлы. Он формирует цель, scope/non-goals, риск, режим, треки, этапы, проверки и stop conditions. Вопросы задавать только при реально блокирующей развилке; безопасные локальные предположения фиксировать и продолжать.

`/apply` выполняет подтверждённый план локально. Commit/push/deploy не подразумеваются без запроса.

`/kodsend` разрешает lifecycle только конкретной согласованной задачи: preflight → task branch → Codex → проверки → Acceptance → REWORK/GO → merge/deploy, если этот путь реально настроен и разрешён. Следовать `rules/codex-orchestration.md`.

## 8. Отчётность

Не выгружать пользователю сырой список из сотен низкоценных замечаний. Сначала показывать результат и P0/P1, затем P2/P3. Для каждой находки: доказательство, сценарий/влияние, первопричина, точное исправление, проверка и уверенность. Использовать шаблоны из `templates/`.

## 9. Справка

При `/kodhelp` или фразе «как пользоваться KodMaster» прочитать `commands/kodhelp.md` и вывести актуальную краткую справку. Полные инструкции: `docs/USER_GUIDE.md` и `docs/DOCUMENTATION.md`.
