# Отладка и регрессионные тесты

## Root cause first

1. Записать точный expected/actual и минимальный сценарий.
2. Воспроизвести текущим test runner или самым дешёвым runnable harness.
3. Составить 2–4 ранжированные, опровержимые гипотезы и одну альтернативную «red-team» гипотезу.
4. Проверять по одному различающему факту; не менять код между измерениями.
5. Зафиксировать причинную цепочку от входа до неверного состояния/выхода.
6. Только затем изменить минимальную точку первопричины.

Если воспроизведение невозможно, создать characterization test вокруг наблюдаемого контракта либо пометить вывод `NEEDS_VERIFICATION`. После трёх неудачных исправлений остановиться и пересмотреть модель системы.

## Выбор теста

Использовать самый низкий уровень, который надёжно ловит регрессию:

- unit — чистая логика и boundary conditions;
- integration — БД, API, очередь, filesystem, несколько модулей;
- component — состояния и поведение UI;
- E2E — критический пользовательский путь и интеграция слоёв;
- property/fuzz — парсеры, сериализация, сложные инварианты;
- characterization — legacy-поведение перед безопасным рефакторингом.

Сначала доказать, что тест красный без исправления, затем зелёный с ним. Не привязывать assertion к внутренней реализации, если можно проверить публичное поведение.

## Обязательные случаи

Happy path, пустые/граничные значения, invalid input, permission denied, timeout/retry, partial failure, duplicate/idempotent request, concurrency — только если применимо. Фиксировать time/random/network; избегать sleep и общей mutable fixture.

## Проверка исправления

Выполнить focused test → связанный suite → lint/typecheck/build по риску. Затем variant sweep: найти другие callers, похожие sinks, дублированные validators и соседние состояния. Не делать «заодно» несвязанный cleanup.
