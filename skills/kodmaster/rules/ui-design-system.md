# UI Design System Rules

Этот файл является обязательным стандартом проектирования и проверки пользовательских интерфейсов в КодМастере. Он применяется совместно с `rules/development-rules.md` и `rules/css-architecture.md`.

Цель: создавать интерфейсы, которые выглядят профессионально и цельно, понятны с первого использования, удобно работают на ПК и телефоне и не накапливают хаотичные стили или уникальные одноразовые компоненты.

Основные ориентиры правил: Apple Human Interface Guidelines, Material Design, эвристики юзабилити Nielsen Norman Group и практики Refactoring UI. Эти источники служат направлением для проектирования, но конкретная реализация должна соответствовать существующему дизайн-языку проекта.

## 1. Design Before Code

Перед созданием или существенной переработкой интерфейса определить:

- цель страницы или экрана;
- основное действие пользователя;
- второстепенные действия;
- структуру и приоритет информации;
- необходимые состояния интерфейса;
- ограничения desktop, tablet и mobile.

Запрещено начинать существенную UI-разработку без понимания, кто пользователь, что он должен сделать и какая информация для него главная.

Для небольшой локальной визуальной правки достаточно определить назначение затронутого элемента и ожидаемый результат, без лишнего проектного процесса.

## 2. Visual Hierarchy

Каждый экран должен иметь очевидную визуальную иерархию.

Пользователь за первые секунды должен понимать:

1. Что это за экран.
2. Что здесь главное.
3. Что нужно сделать дальше.

Иерархия создается через:

- размер;
- положение;
- контраст;
- пространство;
- типографику;
- ограниченный цветовой акцент.

Запрещено делать все элементы одинаково заметными или давать одинаковый визуальный вес основным и второстепенным действиям.

## 3. Minimalism Without Emptiness

Интерфейс должен быть чистым, понятным и функциональным.

Запрещено:

- добавлять элементы только ради украшения;
- перегружать экран декоративными блоками;
- дублировать информацию без пользы;
- создавать пустые визуальные зоны, которые ухудшают композицию и не помогают иерархии.

Каждый элемент должен иметь понятную пользовательскую функцию.

## 4. Premium Visual Quality

Для цельного и качественного внешнего вида использовать:

- согласованные отступы;
- аккуратную типографику;
- единый стиль компонентов;
- качественные иконки;
- согласованные радиусы, границы и тени;
- мягкие и понятные состояния взаимодействия.

Избегать:

- случайных цветов;
- разных радиусов без причины;
- хаотичных размеров;
- необработанных стандартных компонентов, выбивающихся из системы;
- визуальных эффектов, не соответствующих продукту.

Качество достигается системностью, а не количеством декора.

## 5. Layout System

Интерфейсы строятся на повторяемой системе:

- сетки;
- отступов;
- размеров;
- контейнеров;
- компонентов.

Правила:

- одинаковые элементы имеют одинаковые размеры и внутренние отступы;
- одинаковые группы используют одинаковые расстояния;
- страница строится из повторяемых компонентов и токенов;
- новые значения отступов и размеров не создаются произвольно, если уже существует подходящий токен или паттерн.

Запрещено вручную подбирать каждый отступ как уникальное значение и создавать хаотичную верстку.

## 6. Desktop Structure

На больших экранах использовать пространство осмысленно.

Допустимы:

- несколько колонок;
- боковые панели;
- расширенные таблицы;
- плотные рабочие интерфейсы;
- дополнительный контекст рядом с основным действием.

Не делать без причины:

- элементы, растянутые на всю ширину экрана;
- чрезмерно длинные строки текста;
- большие пустые области, нарушающие композицию;
- мобильный одноколоночный макет на широком экране, если рабочая задача выигрывает от дополнительной структуры.

## 7. Mobile Adaptation

Мобильная версия не должна быть уменьшенной копией desktop.

При адаптации можно и нужно менять:

- расположение блоков;
- плотность информации;
- навигацию;
- приоритет второстепенных действий;
- размеры интерактивных элементов;
- представление сложных таблиц.

На телефоне:

- главное действие должно быть легко доступно;
- основные элементы управления должны иметь достаточную область нажатия;
- интерфейс не должен требовать точного попадания мышью;
- сложные таблицы должны иметь мобильный сценарий: карточки, горизонтальный скролл, сокращенный набор колонок или другой подходящий паттерн.

## 8. Responsive Behavior

Для интерфейса должны быть определены сценарии как минимум для трех классов ширины:

- Desktop: широкие рабочие экраны, ориентир около 1920 px;
- Tablet: ориентир 768–1024 px;
- Mobile: ориентир 320–480 px.

Это ориентиры, а не требование жестко использовать именно эти breakpoint-значения. Использовать существующую breakpoint-систему проекта, если она есть.

Для каждого состояния определить:

- что остается;
- что перестраивается;
- что переносится;
- что скрывается только при реальной необходимости;
- как сохраняется доступ к ключевым действиям.

## 9. Component Consistency

Одинаковые сущности должны использовать общие компоненты.

Примеры:

Button:
- primary;
- secondary;
- danger.

Card:
- единый базовый стиль;
- согласованные отступы;
- понятные варианты.

Input:
- единая структура;
- единые состояния focus, disabled, error и success;
- единое отображение подсказок и ошибок.

Запрещено создавать уникальные кнопки, карточки, поля и стили для одинаковых задач без обоснованной причины.

Перед созданием нового UI-компонента найти существующий и проверить возможность его переиспользования или расширения.

## 10. Interaction Feedback

Любое значимое действие пользователя должно иметь обратную связь.

Применимые состояния:

- hover;
- focus;
- pressed;
- disabled;
- loading;
- success;
- error.

Пользователь не должен гадать, был ли клик принят, выполняется ли операция и завершилась ли она.

Обратная связь должна быть быстрой, понятной и не блокировать интерфейс дольше необходимого.

## 11. Animation Rules

Анимация используется для улучшения понимания состояния и пространственной связи элементов.

Допустимо:

- плавное появление и скрытие;
- переход между состояниями;
- обратная связь на действие;
- движение, объясняющее изменение расположения.

Запрещено:

- декоративное движение без функции;
- чрезмерные эффекты;
- анимации, замедляющие выполнение задачи;
- постоянные отвлекающие движения.

Учитывать системную настройку reduced motion, если технология проекта это поддерживает.

## 12. Forms UX

Формы должны быть понятными без дополнительного обучения.

Обязательно:

- ясные названия полей;
- понятные форматы и подсказки там, где они нужны;
- валидация;
- понятное объяснение ошибки;
- сохранение введенных данных при исправимой ошибке, если это возможно;
- явное состояние отправки.

Ошибка должна помогать понять:

- что произошло;
- где проблема;
- как ее исправить.

Не использовать placeholder как единственную подпись важного поля.

## 13. Empty / Loading / Error / Success States

Каждый экран или компонент должен иметь применимые состояния.

### Loading
Понятно, что операция выполняется. Не показывать бесконечную загрузку без объяснения или восстановления.

### Empty
Понятно, почему данных нет и что пользователь может сделать дальше.

### Error
Понятно, что произошло и какое действие доступно для восстановления.

### Success
Если пользователь ожидает подтверждение операции, результат должен быть явно подтвержден.

Не добавлять состояния механически, если компонент в принципе не может в них попасть.

## 14. Navigation

Навигация должна быть предсказуемой и согласованной.

Пользователь должен понимать:

- где он находится;
- куда может перейти;
- как вернуться;
- какое действие является следующим.

Запрещено менять расположение одинаковой навигации между экранами без причины и прятать ключевые действия за неожиданными паттернами.

## 15. Tables and Data

Для больших наборов данных по необходимости использовать:

- фильтры;
- поиск;
- сортировку;
- пагинацию или другой контролируемый способ загрузки;
- закрепление важных колонок;
- сохранение понятного контекста при горизонтальном скролле.

Запрещено выводить огромные таблицы без средств управления, если пользователь должен искать или сравнивать данные.

На мобильных устройствах обязательно определить отдельный сценарий для широкой таблицы.

## 16. Accessibility

Интерфейс должен учитывать базовую доступность.

Обязательно:

- достаточная читаемость текста;
- достаточный контраст;
- клавиатурная доступность интерактивных элементов;
- видимый focus;
- понятные подписи элементов управления;
- корректная семантика там, где она поддерживается;
- достаточная область нажатия для сенсорных устройств.

Запрещено:

- использовать цвет как единственный способ передать важное состояние;
- создавать действия, доступные только мышью;
- делать текст или элементы управления неоправданно мелкими;
- скрывать смысл только в иконке, если она неочевидна и не имеет подписи или accessible name.

## 17. Final UI Review

Перед завершением значимой UI-задачи провести пропорциональный UI review.

### Визуально
Проверить:

- профессионально ли выглядит интерфейс;
- есть ли ясная иерархия;
- выдержана ли единая система;
- нет ли перегрузки или случайных элементов;
- согласованы ли отступы, размеры, радиусы, типографика и иконки.

### UX
Проверить:

- понятно ли основное действие;
- легко ли пройти главный пользовательский сценарий;
- есть ли необходимые состояния;
- понятны ли ошибки и восстановление после них;
- нет ли ненужных шагов.

### Responsive / Mobile
Проверить:

- не ломается ли структура на узких экранах;
- доступны ли ключевые действия;
- удобно ли нажимать на элементы;
- корректно ли преобразуются таблицы, формы и навигация.

### Accessibility
Проверить применимые аспекты клавиатуры, focus, контраста, подписей и семантики.

Для небольшой локальной UI-правки не требуется полный аудит всего приложения. Проверяется затронутый компонент, его состояния и релевантные размеры экрана.



## 18. CSS Legacy Normalization

Канонические правила CSS architecture и legacy normalization находятся в `rules/css-architecture.md`. Этот UI-стандарт не дублирует их. При любом legacy CSS issue Rule Router обязан загрузить `rules/css-architecture.md` до изменения.

## 19. Modal / Overlay Contract

Все модальные окна должны опираться на единый viewport-контракт и по возможности на общий modal primitive.

Обязательно определить:

- границы viewport и safe area;
- max-height/max-width;
- единственного владельца вертикальной прокрутки;
- поведение header/body/footer;
- доступность footer и основных действий;
- мобильное поведение;
- keyboard/focus behavior, если применимо.

Если старые окна собраны по-разному, при исправлении переводить затронутые окна на общий контракт, сохраняя их визуальный дизайн, если редизайн не запрошен.

## 20. Single UI Ownership

Один экран или состояние не должны одновременно контролироваться несколькими независимыми render/load/bind цепочками.

Должен существовать один канонический owner для:

- route/screen activation;
- state;
- data loading;
- render;
- event binding/subscriptions;
- cleanup/lifecycle.

Не использовать повторные render wrappers, monkey patches, повторную инициализацию через таймеры и параллельные full-load механизмы как постоянную архитектуру.

## 21. Visual Preservation During Refactoring

Архитектурный рефакторинг существующего UI не равен редизайну.

Если пользователь не попросил изменить дизайн:

- существующий подтвержденный внешний вид считается визуальным контрактом;
- перед рефакторингом зафиксировать релевантные screenshots/states;
- после изменения сравнить тот же сценарий;
- исправлять архитектуру CSS, render, state, modal или lifecycle, не меняя визуал без необходимости.

Допустимы визуальные изменения только там, где текущий вид сам является дефектом или пользователь отдельно согласовал редизайн.

## Применение в КодМастере

При любой существенной задаче по интерфейсу КодМастер должен:

1. Найти существующую дизайн-систему, компоненты, tokens и исходные стили проекта.
2. Не создавать параллельный дизайн-язык без явного требования.
3. В плане указать применимые UI-правила и необходимые desktop/mobile состояния.
4. Учитывать `rules/development-rules.md`, `rules/testing.md`, `rules/performance.md`, `rules/css-architecture.md` и применимые правила 24–27.
5. После реализации выполнить пропорциональную UI-проверку.
6. Для специального аудита использовать команду `/uiaudit`.
7. В legacy UI отдельно проверять CSS override graph, render ownership, modal viewport contract и риск визуальной регрессии.
