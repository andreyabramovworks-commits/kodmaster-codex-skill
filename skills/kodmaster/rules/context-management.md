# Context Management and Loading Policy

- Не удалять контекст автоматически.
- `/compress` и `/clean` выполнять только по явной команде.
- Сначала анализ, затем применение.
- Сохранять архитектурные решения, ограничения, причины ошибок и следующие шаги.
- Не хранить большие повторяющиеся логи, если сохранены релевантные фрагменты и вывод.
- Project memory не заменяет исходный код и документацию.

## Context Loading Policy

Приоритеты:

1. Не пропустить применимое обязательное правило.
2. Получить достаточные доказательства.
3. Только после этого экономить токены и время.

### Fast

Стартовать с `rules/core.md`, команды, Rule Router и всех обязательных packs. Обычно достаточно 1–2 reference profiles, но это не жёсткий лимит. Если обнаружен риск другого слоя, прочитать его правила сразу.

### Adaptive

Стартовать с core, команды, всех вероятно применимых rule packs и 1–3 наиболее полезных reference profiles. При сомнении о правиле с последствиями для correctness/security/data/deploy — читать.

### Deep

Сначала построить карту стека и компонентов. Затем прочитать все rule packs и profiles, применимые к реально найденным технологиям и потокам. Не читать отсутствующий Redis/WebSocket/Supabase только ради формальной полноты.

### Запрещено

- устанавливать жёсткий token cap, из-за которого можно пропустить нужное правило;
- читать весь репозиторий или все profiles только «на всякий случай»;
- считать уже знакомое правило прочитанным, если его канонический pack не был загружен в текущем task context;
- продолжать изменение нового слоя после его обнаружения без повторного Rule Router.
