# Development Workflow

1. Исходный код изменяется только локально в репозитории.
2. Перед публикацией выполняются релевантные тесты и сборка Docker, если Docker является частью проекта.
3. Для обычного `/apply` проверенные изменения отправляются в GitHub только по отдельной команде; для `/kodsend` это разрешение входит в саму команду.
4. `main` является единственным источником production, если проектная память не фиксирует иное.
5. Сервер получает изменения из репозитория, пересобирает контейнеры и применяет Alembic.
6. После деплоя проверяются health endpoints, контейнеры, миграции и UI.
7. Не смешивать разработку, публикацию и деплой в одно неявное действие.
8. Если проект отличается от этих правил, зафиксировать отличие в project memory или decisions до выполнения.


## КодМастер v3 — Codex task workflow

Для задач, отправленных через `/kodsend`, использовать отдельную ветку от актуального `main`. После доказательного `GO` ветка автоматически сливается в `main`, затем `main` push-ится и запускает production pipeline. Pull Request не требуется.

`/kodsend` является отдельным явным разрешением на полный lifecycle согласованной задачи. Это не отменяет запрет на самовольный deploy для задач, выполняемых обычным `/apply`.

Перед первой Codex-задачей обязателен GitHub bootstrap по `rules/codex-orchestration.md`.
