# Development Rules

Этот файл содержит обязательные правила разработки. Они применяются при планировании, реализации, аудите, публикации и развертывании. Если проект имеет подтвержденное исключение, оно должно быть заранее зафиксировано в `.codex/project-memory.md` или `.codex/decisions.md`.

## 1. Source Code Management

Исходный код изменяется только в локальном репозитории.

Запрещено:

- редактировать файлы напрямую на production-сервере;
- вносить изменения вне Git workflow;
- использовать production как рабочую среду разработки;
- выполнять незафиксированные ручные правки, которые невозможно воспроизвести из Git.

## 2. Local Validation

Перед публикацией необходимо выполнить локальную проверку, относящуюся к измененной области:

- запустить релевантные тесты;
- проверить сборку приложения;
- собрать Docker-контейнеры, если Docker используется проектом;
- проверить отсутствие ошибок сборки, запуска и критических предупреждений;
- проверить измененный пользовательский сценарий.

Публиковать непроверенные изменения запрещено.

Если какую-либо проверку выполнить невозможно, это нужно явно указать в итоговом отчете вместе с причиной и риском.

## 3. Git Workflow

Для обычного `/apply` после успешной проверки и только по отдельной команде пользователя:

1. Проверить состав изменений.
2. Создать осмысленный commit.
3. Отправить изменения в GitHub.
4. Использовать историю Git как единственный воспроизводимый источник изменений.

Для задач, отправленных через `/kodsend`, сама команда `/kodsend` является явным разрешением на полный Git lifecycle согласованной задачи: task branch, commit, push, audit, merge в `main`, push `main` и production workflow после `GO`.

Запрещено автоматически выполнять commit, push, merge или публикацию вне этих двух случаев.

## 4. Production Deployment

Ветка `main` является единственным источником production-развертывания.

Другие ветки не используются для production.

Если конкретный проект работает иначе, это должно быть подтверждено пользователем и записано в проектную память до выполнения деплоя.

## 5. Deployment Pipeline

После появления подтвержденного commit в `main` сервер должен:

1. Получить изменения из репозитория.
2. Пересобрать Docker-контейнеры.
3. Выполнить миграции Alembic.
4. Запустить или перезапустить приложение штатным способом проекта.

Skill не должен подменять этот процесс ручным редактированием production-файлов.

## 6. Post Deployment Check

После развертывания необходимо проверить:

- состояние контейнеров;
- health endpoints;
- выполнение миграций;
- отсутствие критических ошибок в логах запуска;
- работу измененного пользовательского сценария;
- работу пользовательского интерфейса.

Деплой нельзя считать завершенным только по факту успешной команды запуска.

## 7. Security Rules

Запрещено хранить в Git:

- `.env`;
- пароли;
- API-ключи;
- OAuth-токены;
- SSH-ключи;
- приватные сертификаты;
- cookies и session tokens;
- backup-файлы с данными или секретами.

Все секреты должны находиться только:

- в защищенном окружении;
- в backend configuration;
- в secret storage;
- в другом предусмотренном проектом защищенном хранилище.

Дополнительно:

- не выводить секреты из HAR, логов и конфигурации в ответе;
- при обнаружении секрета не повторять его значение;
- сообщить о риске и рекомендовать ротацию;
- не ослаблять авторизацию, проверку ролей или валидацию ради устранения симптома.

## 8. Database Changes

Любое изменение структуры PostgreSQL разрешено только через Alembic migration.

Запрещено:

- вручную изменять production-базу данных;
- изменять схему без миграции;
- выполнять необратимые изменения без анализа последствий;
- скрывать изменение схемы внутри обычного application-кода.

Миграция должна:

- иметь понятный `upgrade`;
- иметь безопасный `downgrade`, если это поддерживается проектом;
- учитывать существующие данные;
- проверяться локально или в безопасном тестовом окружении;
- учитывать обратную совместимость при поэтапном деплое.

## 9. External API Integration

Интеграции с Bitrix24 и другими внешними сервисами разрабатываются через backend API.

Правила:

- секреты хранятся только на backend;
- OAuth-токены находятся только в protected environment или защищенном хранилище;
- frontend никогда не получает приватные ключи и служебные токены;
- формат внешнего API нельзя менять без анализа потребителей;
- ошибки, таймауты, повторные запросы и ограничения API должны обрабатываться явно;
- приватные данные из HAR и логов нельзя переносить в код или документацию.

## 10. CSS / UI Architecture

### Запрет дублирования и наслоения стилей

Запрещено:

- создавать новые стили поверх существующих;
- исправлять визуальные проблемы добавлением дополнительных CSS-слоев;
- создавать конфликтующие или дублирующие классы;
- повышать специфичность только для обхода причины;
- использовать `!important` как способ скрыть архитектурную проблему;
- оставлять неиспользуемые стили после исправления.

Ситуация, в которой новый CSS-слой нужен только для переопределения существующего, считается ошибкой архитектуры, а не допустимой необходимостью.

Правило:

Существующий стиль должен быть:

1. Найден.
2. Проверен вместе с точками использования.
3. Переиспользован.
4. Изменен в исходном источнике и в одном месте.
5. Проверен на связанных компонентах и состояниях.

При изменении дизайна необходимо менять исходный источник стиля, а не создавать новый слой.

Новый стиль допустим только для действительно нового визуального элемента, у которого отсутствует подходящий существующий источник. Он не должен дублировать или переопределять существующую реализацию.

## 11. Code Reuse Rule

### Запрет копирования кода

Запрещено:

- копировать одинаковую логику в несколько файлов;
- создавать одинаковые функции с небольшими отличиями;
- дублировать валидацию, запросы, преобразование данных или бизнес-правила;
- исправлять копии одной логики по отдельности.

Перед созданием нового кода необходимо:

1. Найти существующую реализацию.
2. Проверить ее точки использования и ответственность.
3. Использовать ее повторно.
4. При необходимости расширить через:
   - параметры;
   - композицию;
   - наследование, только если оно соответствует архитектуре проекта;
   - отдельные сервисы;
   - общие функции, hooks или utilities.
5. Создать новую реализацию только при действительно различной ответственности или несовместимых требованиях.

Один источник логики означает одно место изменения.

## 12. Clean Code Architecture

Код должен быть разделен по ответственности.

Запрещено:

- создавать большие файлы с разнородной логикой;
- оставлять «полотна» кода;
- смешивать UI, бизнес-логику, сетевые запросы и работу с данными;
- помещать всю реализацию функции в страницу или точку входа;
- проводить несвязанный рефакторинг внутри локального исправления.

Основной файл должен содержать только:

- структуру;
- вызовы;
- связывание компонентов;
- минимальную координацию.

Логика должна находиться в отдельных модулях по ответственности.

Плохо:

```text
UserPage.tsx

500 строк:
- запросы;
- обработчики;
- стили;
- бизнес-логика;
- преобразование данных.
```

Хорошо:

```text
UserPage.tsx
├── components/
├── services/
├── hooks/
├── utils/
└── api/
```

Каждый модуль отвечает за одну понятную задачу. При этом нельзя дробить код механически: выделение модуля должно улучшать ответственность, повторное использование, тестируемость или читаемость.


## 13. Deployment Artifact и Rollback

Каждый production-деплой должен быть привязан к конкретному commit SHA или неизменяемой версии Docker-образа.

Обязательно:

- фиксировать, какой commit или Docker image развернут;
- иметь понятную процедуру возврата на предыдущую стабильную версию;
- выполнять rollback через Git/Docker workflow;
- не редактировать production-сервер вручную для восстановления;
- после rollback повторно проверять контейнеры, health endpoints, миграции и затронутый пользовательский сценарий.

Если безопасный rollback невозможен, это должно быть выявлено до деплоя и явно отражено в плане и рисках.

## 14. Observability, Logs и Error Monitoring

Приложение должно иметь достаточную наблюдаемость для диагностики проблем:

- структурированные логи;
- логирование ошибок backend и frontend;
- health endpoints;
- проверку состояния Docker-контейнеров;
- понятные сообщения об ошибках для пользователя.

В логах запрещено хранить:

- пароли;
- API-ключи;
- OAuth-токены;
- session tokens;
- персональные данные без обоснованной необходимости;
- другие секреты и чувствительные значения.

Логи должны помогать найти причину ошибки, но не раскрывать защищенные данные.

## 15. Dependency Management

Новые зависимости добавляются только при реальной необходимости.

Правила:

- использовать lock-файлы;
- фиксировать версии зависимостей согласно правилам проекта;
- не добавлять библиотеку ради небольшой логики, которую можно безопасно реализовать существующими средствами;
- перед добавлением проверить, не используется ли уже подходящая библиотека;
- при обновлении зависимостей проверить совместимость;
- проверить известные уязвимости доступными средствами проекта;
- не выполнять массовое обновление зависимостей внутри несвязанной локальной задачи.

Добавление зависимости должно быть отражено в плане и итоговом отчете вместе с причиной.

## 16. API Contracts и Backward Compatibility

Backend API должен иметь понятные и единообразные контракты запросов и ответов.

При изменении API необходимо:

- валидировать входные данные;
- возвращать предсказуемые ошибки;
- не ломать существующий frontend без одновременного обновления;
- сохранять обратную совместимость, если frontend и backend могут развертываться в разное время;
- документировать сложные, публичные или интеграционные endpoints;
- учитывать существующих потребителей API;
- проверять форматы успешных и ошибочных ответов.

Ломающие изменения должны быть явно обозначены и согласованы до реализации.

## 17. Test Strategy

Проверка выбирается по риску и масштабу изменения.

Возможные уровни проверки:

- unit-тесты – для бизнес-логики, утилит и сервисов;
- integration-тесты – для API, базы данных и интеграций;
- e2e-тесты – для критичных пользовательских сценариев;
- ручная проверка – для небольших UI-изменений или простых правок.

Если исправляется баг, по возможности добавляется тест, предотвращающий его повторное появление.

Не требуется запускать все виды тестов для каждого изменения. Перед commit необходимо выполнить достаточную проверку и убедиться, что изменение не ломает приложение.

Если тест не добавлен или проверка ограничена, причина и остаточный риск указываются в итоговом отчете.

## 18. External API Reliability

Интеграции с Bitrix24 и другими внешними сервисами должны обрабатываться устойчиво.

При необходимости использовать:

- таймауты запросов;
- обработку сетевых ошибок;
- ограниченные повторные попытки при временных сбоях;
- обработку rate limit;
- idempotency для операций, которые могут быть отправлены повторно;
- безопасное логирование без секретов.

При недоступности внешнего сервиса приложение должно показывать понятную ошибку и не должно падать целиком.

Повторные попытки не должны быть бесконечными и не должны дублировать необратимые операции.

## 19. Performance Rules

При разработке необходимо избегать очевидных проблем производительности:

- не загружать большие объемы данных без необходимости;
- использовать пагинацию для списков;
- не допускать N+1 запросов к базе данных;
- добавлять индексы для новых тяжелых запросов, когда это обосновано;
- не выполнять тяжелую логику в UI без необходимости;
- использовать lazy loading для крупных frontend-модулей, когда это оправдано;
- не проводить преждевременную оптимизацию без подтвержденной проблемы.

Оптимизация выполняется по необходимости, но новые решения не должны создавать очевидный технический долг по производительности.

## 20. UI Quality и Accessibility

Для всех существенных UI-задач дополнительно обязателен стандарт `rules/ui-design-system.md`. Это правило задаёт базовый минимум, а отдельный UI-стандарт подробно определяет визуальную иерархию, layout, desktop/mobile, responsive, компоненты, feedback, формы, состояния, навигацию, таблицы, animation и accessibility.

Каждый интерфейс должен учитывать применимые состояния:

- loading;
- empty;
- error;
- success, если пользователь ожидает результат действия.

Также необходимо:

- показывать понятные ошибки в формах;
- добавлять подтверждение опасных действий;
- обеспечивать корректную работу на мобильных устройствах, если интерфейс их поддерживает;
- не создавать элементы управления, доступные только мышью;
- соблюдать базовую читаемость, контраст и понятность интерфейса;
- сохранять клавиатурную доступность интерактивных элементов.

Для локальной визуальной правки проверяются только затронутые состояния и устройства, если более широкий риск отсутствует.

## 21. Architecture Decision Records

Для важных архитектурных решений необходимо кратко фиксировать:

- какую проблему решает решение;
- почему выбран именно этот вариант;
- какие альтернативы рассматривались;
- какие ограничения или последствия появились.

Документация должна быть короткой и храниться в Git рядом с проектом.

В КодМастере такие решения фиксируются в `.codex/decisions.md` или в принятом проектом формате ADR.

Не требуется создавать ADR для каждой мелкой правки. Запись нужна, когда решение влияет на архитектуру, интеграции, данные, безопасность, инфраструктуру или долгосрочные ограничения.

## 22. CI Validation

Автоматические проверки в CI используются, когда они настроены и необходимы для изменения.

CI может включать:

- lint;
- formatting;
- type checking;
- tests;
- production build;
- Docker build;
- security или dependency scan.

Не требуется включать все проверки для каждой маленькой задачи. Для рискованных изменений – базы данных, авторизации, API, интеграций, Docker и production-конфигурации – проверка должна быть полной в рамках доступного pipeline.

Если CI не настроен или недоступен, это не скрывается: выполняются доступные локальные проверки и фиксируется остаточный риск.

## 23. Definition of Done

Изменение считается полностью завершенным после выполнения применимых пунктов:

- код реализован;
- выполнена достаточная ручная или автоматическая проверка;
- создана Alembic migration, если изменилась структура БД;
- проверено отсутствие секретов в Git;
- для обычного `/apply` создан commit/push только если пользователь отдельно разрешил публикацию;
- для `/kodsend` после статуса `GO` task-ветка автоматически слита в `main`, `main` отправлен в GitHub и выполнен настроенный production-deploy;
- выполнена post-deployment проверка контейнеров, health endpoints, миграций и затронутого пользовательского сценария.

Если задача выполняется через обычный `/apply` и commit/push/deploy не были разрешены, техническая реализация может быть завершена, но полный Definition of Done не достигнут. Для `/kodsend` разрешение на эти действия уже входит в lifecycle задачи после `GO`.

## Дополнительное правило для Codex: проверки по уровню риска

Проверки должны соответствовать уровню риска.

Не применять тяжелые процессы без необходимости.

Цель:

- надежность критичных изменений;
- экономия времени и токенов при простых правках.

Практическое применение:

- низкий риск – локальная проверка измененного файла или сценария;
- средний риск – релевантные тесты, type checking или сборка затронутой части;
- высокий риск – полный набор применимых тестов, production build, Docker, миграции, security/dependency checks и post-deployment verification.

Skill обязан в плане указать уровень риска и достаточный набор проверок. Он не должен автоматически выбирать самый тяжелый процесс только потому, что он существует.

## Применение правил в планировании

Перед выполнением задачи Skill должен проверить, какие разделы этого файла относятся к изменению, и отразить их в плане.

Примеры:

- проблема CSS требует поиска исходного источника стиля до изменения;
- изменение PostgreSQL требует Alembic migration;
- интеграция Bitrix24 требует backend API;
- публикация требует локальных проверок; для `/apply` нужна отдельная команда, для `/kodsend` разрешение уже дано самим `/kodsend`;
- набор тестов и CI-проверок выбирается по уровню риска;
- production-деплой требует идентифицируемого артефакта и понятного rollback;
- изменение API требует проверки контрактов и обратной совместимости;
- крупный компонент требует проверки разделения ответственности;
- новая логика требует поиска существующей реализации.

Если запрос пользователя противоречит этим правилам, Skill должен остановиться, объяснить риск и предложить безопасный способ выполнения.


## 24. CSS Legacy Normalization

Если в затронутой области уже существуют цепочки CSS-переопределений, большое количество `!important`, несколько источников одного стиля, fix/version/override-файлы, повторяющиеся произвольные значения или конкурирующие media queries, запрещено добавлять еще один корректирующий слой поверх них.

Необходимо:

1. Зафиксировать фактический итоговый визуал и поведение затронутой области.
2. Найти все CSS-правила, которые формируют этот результат.
3. Определить один канонический источник стиля или компонентный primitive.
4. Перенести в него требуемое итоговое поведение.
5. Удалить ставшие лишними override-правила только в затронутой области.
6. Проверить визуальную и responsive-эквивалентность до и после.

Запрещено проводить глобальную чистку незатронутого UI без отдельного согласования. Цель – сохранить внешний результат, но убрать архитектурное наслоение.

## 25. Modal / Overlay Viewport Contract

Все модальные окна, dialogs, drawers и аналогичные overlays одного приложения должны использовать единый канонический primitive или общий контейнер, если проектом не обосновано иное.

Контракт должен определять:

- позиционирование относительно viewport;
- максимальную ширину и высоту;
- safe area и ограничения встроенной среды, включая Bitrix24, если применимо;
- один предсказуемый владелец вертикальной прокрутки;
- поведение header, body и footer;
- доступность кнопок действия при любой допустимой высоте viewport;
- mobile layout;
- Escape/закрытие, focus management и возврат focus, если технология это поддерживает.

Запрещено без обоснования:

- одновременно прокручивать внешний контейнер модального окна и его body;
- допускать выход header за верх viewport;
- располагать footer ниже доступной области viewport;
- создавать несколько независимых вертикальных scroll-зон внутри одного modal flow;
- исправлять viewport-проблемы отдельными локальными хаками для каждого окна.

## 26. Single UI Ownership

Для одного экрана или пользовательского состояния должен существовать один канонический владелец render, routing, state, загрузки, подписок и lifecycle.

Запрещено:

- иметь несколько конкурирующих render-функций одной ответственности;
- повторно переопределять или monkey-patch канонический renderer как постоянную архитектуру;
- оборачивать render/load-функции несколькими runtime-слоями;
- использовать `setTimeout` для повторной инициализации как постоянное решение lifecycle-проблемы;
- запускать несколько независимых initial/full load одного экрана;
- повторно подключать одинаковые event handlers без гарантированного cleanup или idempotency.

При исправлении legacy-кода необходимо сначала построить цепочку `trigger -> load -> state -> render -> bind`, найти все конкурирующие определения и оставить один канонический сценарий. После рефакторинга проверить отсутствие flicker, двойных запросов, двойных listeners, промежуточного старого DOM и повторного полного render.

## 27. Visual Preservation During Refactoring

Если пользователь просит исправить архитектуру существующего UI и явно не просит редизайн, текущий подтвержденный внешний вид и пользовательское поведение считаются контрактом.

Перед изменением по возможности зафиксировать релевантные:

- desktop/mobile screenshots;
- размеры и положение ключевых элементов;
- состояния;
- взаимодействия;
- пользовательский сценарий.

Разрешено менять внутреннюю реализацию: CSS-архитектуру, компоненты, state ownership, renderer, modal primitive, порядок загрузки и lifecycle.

Без отдельного согласования запрещено менять цвета, композицию, типографику, размеры, отступы или пользовательское поведение, кроме элементов, которые являются непосредственно исправляемым дефектом.

После рефакторинга выполнить пропорциональную визуальную и поведенческую регрессионную проверку.


## 28. Codex Orchestration and Automatic Main Delivery

Для задач, явно отправленных через `/kodsend`, обязательны `rules/codex-orchestration.md` и следующий lifecycle:

1. mandatory GitHub bootstrap/preflight;
2. отдельная task-ветка от актуального `main`;
3. компактный task package;
4. выполнение Codex;
5. evidence-based audit;
6. `REWORK` до устранения подтверждённых дефектов либо `BLOCKED`;
7. `GO`;
8. автоматический merge в `main` без Pull Request;
9. push `main`;
10. production-deploy по реально настроенному pipeline;
11. post-deployment verification и rollback при подтверждённой регрессии.

`/kodsend` считается явным разрешением пользователя на этот полный цикл только для согласованной задачи. Для других задач автоматическое изменение production не разрешается.

Pull Request не является частью стандартного КодМастер v3 workflow, поскольку целевой сценарий предполагает одного разработчика. При этом отдельная ветка, audit gate, commit SHA/deployment artifact и rollback обязательны.
